평가 자동산정 — 설계 결정 · 기술 요약

PeopleCore HR · 공정성 요구가 만든 복잡도를 설계 + 기술로 풀어낸 방식
정직한 프레이밍. 자동산정 파이프라인의 복잡도는 대부분 설계 판단 (통계 공식 적용, 로직 분기, 스키마 설계)이고 "기술 스택" 은 아님. 아래는 ① 공정성 요구가 만든 설계 결정 9개, ② 그 안에서 실제로 녹아있는 기술 3가지, ③ 프로젝트 내 다른 기술 셀링 포인트 후보로 구성.
❌ "자동산정을 이런 기술로 구현했습니다"
✅ "공정성 요구가 만든 복잡도를 이렇게 설계로 분해하고, 그 위에 기술을 얹었습니다"

조목조목 — 설계 결정 9개

1 팀장 평가 성향 편차

A팀장 후함, B팀장 짜다. 단순 합산은 팀 소속이 실력을 덮는 불공정.
Z-score 정규화. 점수를 팀 내 상대 위치로 환산해 편향 제거. 결과는 managerScoreAdjusted 박제.

2 팀 규모 신뢰도

3명 팀의 평균/표편은 통계적으로 무의미. 무작정 보정은 역공정.
minTeamSize 미만 스킵. 원본 유지 + HR 검토 목록(anomalies)에 노출해 수동 보정 유도.

3 전원 동점팀 (σ = 0)

팀장이 전원 동점 부여 시 (x-μ)/σ 에서 0-division 폭발.
σ=0 감지 후 보정 스킵. zeroStdDevTeams 리스트로 HR 대시보드에 표시. 런타임 예외 대신 비즈니스 플로우로 처리.

4 동점자 경계 처리

S 정원 3명인데 3·4위가 동점이면 누구는 S? 명백한 불공정.
같은 점수 = 같은 등급 묶음. 비율 초과해도 윗 등급으로 흡수, 다음 등급 정원에서 차감.

5 비율 라운딩 잔여

13명에 10/20/30/25/15% 를 소수점 없이 나눌 수 없음.
경계 = ceil(총원 × 누적비율). 마지막 등급이 잔여 흡수. 자의적 배정 금지, 규칙 명시.

6 수동 보정 덮어쓰기 방지

HR 의 개별 조정(휴직 배려 등)을 재실행 버튼 한 번이 전부 날림.
cohort diff 기반 멱등성. 변화 없으면 NO_OP, 보정 이력 존재 시 confirm=true 요구.

7 시즌 중 규칙 변경 차단

시즌 오픈 후 HR 이 가중치/비율 수정해 결과 조작 가능.
formSnapshot JSON 박제. 시즌 OPEN 시점 규칙 전체를 직렬화해 저장. 계산 엔진은 박제본만 참조.

8 사후 조작 방지 (감사)

자동 등급을 나중에 임의로 바꾸면 원본 추적 불가. 분쟁 시 답할 수 없음.
autoGrade / finalGrade 분리. 원본 불변 보존, 보정 시 Calibration 이력 INSERT. isCalibrated 플래그 유지.

9 확정 후 불변성

확정 후 수정 가능하면 최종 결과 신뢰성 붕괴.
이중 잠금. Season.finalizedAt + EvalGrade.lockedAt 박제. 이후 수정 API 는 전부 차단.

② 자동산정 안에 실제로 녹아있는 "기술"

위 ①번은 설계 판단 이 맞고 순수 "기술" 은 아님. 단, calculateAutoGrades → applyBiasAdjustment → applyDistribution 파이프라인 내부에 실제로 녹아있는 기술 4가지를 아래에 정리. 각 항목은 면접 질문으로 이어지기 좋은 지점들.

1 JPA dirty checking 기반 대량 UPDATE

전 사원(수백~수천명)의 종합점수·조정점수·등급을 한 번에 갱신. 순진하게 짜면 N번 UPDATE 쿼리 폭주.
단일 트랜잭션 + dirty checking. calculateAutoGrades 내부에서 findBySeason 으로 리스트 로드 후 setter 만 호출, 트랜잭션 종료 시점에 JPA 가 변경 감지로 일괄 flush. hibernate.jdbc.batch_size 설정 시 JDBC 배치 UPDATE 로 묶임.
예상 질문: "N건 UPDATE 에 쿼리 몇 번 나가나요? 부분 실패 시 롤백은? 배치 사이즈 기준은?"

2 BigDecimal 정밀도 · 반올림 제어

가중평균/Z-score/비율 계산에서 소수점 정밀도 깨지면 등급 경계가 어긋남. double 로 하면 0.1+0.2 ≠ 0.3 오차 누적.
전 계산 BigDecimal 강제 + RoundingMode.HALF_UP 명시. 나눗셈은 반드시 divide(scale, roundingMode) 로 스케일 지정. Z-score / KPI 달성률 / 가중평균 모두 정밀도 고정 (예: 소수점 2자리).
예상 질문: "왜 double 안 썼나요? BigDecimal 성능 이슈는?"

3 JPQL 집계 쿼리 (팀/등급 단위 통계)

팀 편향 보정 시 팀별 managerScore 평균/표편 필요. 등급별 카운트도 집계 필요. 전 row 로드 후 Java 루프는 비효율.
JPQL GROUP BY + AVG + 프로젝션 DTO 직접 매핑. findTeamBiasSummary, countByAutoGradeGroup 에서 SELECT new TeamBiasDto(d.deptId, AVG(g.managerScore), ...) 로 DB 단에서 집계. 네트워크 왕복 1번 + Java 루프 없이 해결.
예상 질문: "Java 에서 집계할 때와 DB 집계의 트레이드오프는?"

4 설정 주도형 계산 엔진 (formSnapshot 역직렬화)

회사마다 가중치/비율/조정항목 다름. 하드코딩 X, 시즌 중 규칙 변경 조작도 차단해야 함.
Jackson 으로 FormSnapshotDto 역직렬화 후 런타임 주입. 계산 엔진은 공식을 모름 — snapshot.getAdjustments(), snapshot.getWeights() 를 읽어 동적으로 적용. 시즌 OPEN 시 박제한 JSON 만 참조해 절차적 공정성까지 확보.
예상 질문: "왜 컬럼 스키마 대신 JSON? Jackson 의존 타입 매핑 주의점?"

③ 확장 방향성 (통계 아이디어 · AI · 실제 기술 스택)

정직 분류: 아래 항목들은 성격이 다 다름 — 📊 통계 은 수학 기법, 🤖 AI 는 ML/AI 기술, ⚙️ 기술 은 실제 백엔드/인프라 스택. 면접 시 각 항목이 어느 범주인지 구분해서 말해야 안 털림.

통계·AI 아이디어 (도메인 확장)

1 IQR 이상치 탐지 📊 통계

팀장이 특정인에게만 극단값 부여 — 단순 Z-score 로는 놓침.
IQR × 1.5 박스플롯 방법. Q3 + 1.5 × IQR 초과 / Q1 − 1.5 × IQR 미만을 outlier 로 플래그. Apache Commons Math 라이브러리 한 줄.
정체: 교과서 통계 공식. "통계적 이상치 탐지 아이디어 적용" 으로 포지셔닝.

2 Isolation Forest (ML 이상치 탐지) 🤖 AI

IQR 은 단일 피처 기반. 다차원(점수·피드백길이·제출시각) 복합 이상치 탐지 필요.
Isolation Forest + Smile/Tribuo 라이브러리. 비지도 ML 로 다차원 이상치 점수화. 모델 학습/저장/로딩 파이프라인. 진짜 ML 기술.
정체: ML 알고리즘. 라이브러리 + 튜닝 + 파이프라인으로 기술 셀링 가능.

3 Bootstrap 소규모 팀 보강 📊 통계

3~4명 팀은 표편 신뢰도 낮아 Z-score 스킵 중. 그냥 버리기엔 아까움.
Bootstrap resampling 1000회. 재표본으로 평균/표편 신뢰구간 추정. 구간 좁으면 보정 적용. 통계 n 부족을 컴퓨팅으로 우회.
정체: 응용 통계 기법. 구현은 간단한 루프.

4 Spearman 순위상관 📊 통계

자기평가 3위인데 팀장평가 최하위 → 평가 불일치 감지 불가.
Spearman rank correlation. 상관계수 < 0.3 팀은 "불일치 팀" 플래그. 비모수 통계 공식.
정체: 통계 공식. 난이도 낮음.

5 팀장 Reputation Scoring 📊 로직

팀장별 평가 정확도 편차 존재. 과거 예측 vs 실제 성과 일치도 기반 가중치 조정.
과거 시즌 상관계수 누적 → Reputation Score. 가중평균에서 팀장 가중치를 rep 비례 동적 조정. 베이지안 업데이트.
정체: 비즈니스 로직 + 누적 계산. 설계 아이디어.

6 LLM 피드백 감정 분석 🤖 AI

피드백엔 "탁월함" 쓰고 등급은 C 부여 — 텍스트/등급 불일치 감지 불가.
OpenAI/Claude API 또는 로컬 LLM (Ollama). 피드백 감정 스코어화, 등급 순위와 상관 threshold 미만이면 플래그. 프롬프트 엔지니어링 + 비동기 호출 + 비용 관리. 실전 AI 통합.
정체: AI API 통합 기술. 진짜 기술 셀링 가능.

7 Fairness Metrics 자동 측정 📊 통계

부서/성별/직급에 등급 편향 분포 감지 필요.
Demographic Parity + 카이제곱 독립성 검정. ML 공정성 프레임워크를 HR 도메인에 이식.
정체: 지표 정의 + 통계 검정. 도메인 응용 센스.

8 Explainability JSON 📊 설계

"왜 내가 B 인가요?" 사원 문의 자동 응답 필요.
사원별 등급 산출 과정 JSON 박제. {selfScore, managerScore, zScore, rank, boundary, adjustments, calibration}. SHAP-like 기여도 퍼센트.
정체: 데이터 구조 설계. XAI 개념 차용.

9 Drift Detection 📊 통계

작년 A등급 20% → 올해 5%. 규칙 문제? 조직 문제? 감지 불가.
Kolmogorov-Smirnov 검정 + PSI. 시즌 간 분포 차이 유의성 검증, PSI > 0.2 경고. ML 모니터링 기법 이식.
정체: 응용 통계. ML 모니터링 개념 차용.

진짜 "기술" 로 묶일 수 있는 인프라/백엔드 적용

10 Spring Batch 도입 ⚙️ 기술

자동산정은 본질적으로 배치. 현재는 @Transactional 메서드 하나. 재시작 / 청크 / 실패 스킵 없음.
Job / Step / Chunk 분해. reader-processor-writer 로 나눠 청크 단위 처리. 실패 row skip, 재실행 시 체크포인트 재개, 멀티스레드 Step 병렬.
셀링: "대량 배치 표준 프레임워크 적용으로 운영 안정성 확보"

11 Redis 캐싱 ⚙️ 기술

formSnapshot 역직렬화, 팀별 평균/표편 — 매번 계산하면 낭비.
Spring Cache + Redis. 시즌 ID 키로 파싱 결과 + 팀 통계 캐시. TTL 관리, 규칙 변경 시 캐시 무효화 이벤트.
셀링: "반복 계산 제거 + 인메모리 캐시 계층 분리"

12 CompletableFuture 병렬 계산 ⚙️ 기술

팀 20개 Z-score 를 순차 계산. CPU 코어 놀고 있음.
팀별 Z-score 를 CompletableFuture 로 병렬 실행. ForkJoinPool 튜닝, allOf 로 join. 예외 처리 / 스레드풀 size 관리.
셀링: "동시성 프로그래밍으로 대용량 계산 시간 단축"

13 SSE 진행률 스트리밍 ⚙️ 기술

자동산정 버튼 누르고 N초 동안 화면 멈춤. 진행 상황 불투명.
Server-Sent Events. SseEmitter 로 단계별 진행률 실시간 전송 ("계산 30%", "보정 중"). 프론트 EventSource 구독.
셀링: "단방향 스트리밍으로 UX 개선, WebSocket 대비 경량"

14 Testcontainers 통합 테스트 ⚙️ 기술

자동산정 계산 정확성을 H2 로는 검증 어려움. MySQL 전용 함수/집계 쿼리 정확도.
Testcontainers MySQL. 실제 MySQL 컨테이너 띄워 JUnit5 통합 테스트. Z-score / 강제배분 결과를 기대값과 비교. CI 자동 실행.
셀링: "실환경 통합 테스트로 계산 정확성 회귀 방어"

15 Prometheus + Grafana 모니터링 ⚙️ 기술

자동산정 배치 실행 시간 / 실패율 / 사원 수 변화를 운영 중 파악 불가.
Micrometer + Prometheus. 배치 메트릭 (batch.duration, batch.rows, batch.errors) 노출. Grafana 대시보드 + 알람.
셀링: "운영 관찰성 확보 + SLO 기반 알람"

16 Hibernate StatelessSession ⚙️ 기술

수천 사원 EvalGrade 를 persistence context 에 다 올리면 메모리 폭증 / dirty checking 비용.
StatelessSession + JDBC batch. 영속성 컨텍스트 없이 직접 UPDATE 발행. batch_size 와 조합해 대량 처리 최적화.
셀링: "JPA 한계 인지 + 상황별 세션 타입 선택"

17 Python ML 서비스 gRPC 연동 ⚙️ 기술

Java 네이티브 ML 라이브러리는 Python 대비 생태계 빈약. 고급 모델은 Python 로.
FastAPI + scikit-learn ML 서비스 + gRPC. Java(Spring) 가 gRPC 클라이언트로 호출, Python 이 Isolation Forest / 감정 분석 수행. 언어 간 책임 분리.
셀링: "폴리글랏 아키텍처 + 언어별 강점 활용"
면접 대응 팁. 전부 구현 안 해도 됨 — "이렇게 확장할 수 있다" 로 성장 가능성 어필용. 발언 시 뱃지 구분해서 말하기: 📊 통계 는 "이런 통계 기법으로 개선 여지", 🤖 AI 는 "AI 연동까지 확장 가능", ⚙️ 기술 은 "운영 안정성/성능 위해 이런 기술 도입 계획". 섞어 말하면 "저거 기술 맞냐?" 반박 들어옴.

인터뷰 말투 버전
